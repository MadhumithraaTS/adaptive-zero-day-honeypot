# Collection Protocol

How the sessions were produced, captured and turned into features, in enough detail to reproduce
the dataset.

## 1. Environment

| Component | Detail |
|---|---|
| Honeypot | Cowrie SSH honeypot, Docker image `cowrie/cowrie:latest` (image created {cowrie_image_created}, source revision `{cowrie_revision}`) |
| Exposure | Container port 2222 published on host `127.0.0.1:2223`; **no internet exposure** |
| Authentication | `auth_class = UserDB` with the supplied `metadata/cowrie_userdb.txt`: any credentials accepted except four reserved `scan` username/password pairs, which are rejected to produce realistic failed logins |
| Client | Python 3 with `paramiko`, running on the same host |
| Source address seen by Cowrie | `172.19.0.1` (the Docker bridge gateway) for **every** session |

## 2. Generation

Sessions were generated by `dataset_builder/generate_labelled_traffic.py` in the project repository
using the profiles in `metadata/generation_profiles.json`.

| Split | Seed | Generated sessions | Held-out profiles | Speed | Collected (UTC) |
|---|---|---|---|---|---|
{runs_table}

For each generated session the client:

1. Picks a profile (benign is weighted 3:1 against each attack profile).
2. Makes 0–5 deliberately failed login attempts, each on its own connection.
3. Logs in with credentials drawn from the profile, opens an interactive shell, sends the planned
   commands with random delays drawn from the profile's delay range, then sends `exit`.
4. Appends a record to `generation_manifest.jsonl`.

**Speed.** All delays were divided by the `speed` factor (8) to make collection practical. Relative
pacing between profiles is preserved (benign sessions remain the slowest, botnet and brute-force the
fastest), but **absolute timing values are about 8× shorter than human pacing**. Keep this in mind
before comparing timing features with real-world captures.

Sessions run strictly one after another; nothing runs in parallel.

## 3. Capture and isolation

Cowrie appends every event to one cumulative JSON log that is never cleared. To isolate a run:

1. Before generating, the client records the number of lines already in the log
   (`log_baseline_lines` in `run_meta.json`).
2. After generating, the full log is copied out and only lines after the baseline are kept.
3. A secondary filter drops any session whose connect time falls outside the run's time window
   (plus 15 s). In v1.0.0 this removed 74 sessions from the train collection (traffic that reached
   the honeypot after the run ended) and none from the eval collection.

## 4. Parsing and features

1. Events are grouped by Cowrie session ID (`sessions.jsonl` keeps the raw events per session).
2. Labels are attached as described in `docs/ANNOTATION_GUIDELINES.md`.
3. Features are computed per session by the project's `scripts/extract_features.py` and written to
   `features.csv`. See `metadata/data_dictionary.csv` for every column.

The feature names follow the UNSW-NB15 convention, but they are computed from **Cowrie application
events, not from packet capture**. Several are proxies or constants; the data dictionary says which.

## 5. Ethics and safety

- No real attackers, users or third parties are involved. All traffic was generated by the authors
  against their own isolated honeypot.
- IP addresses and domains inside commands are arbitrary placeholders chosen to look plausible; some
  are real public addresses. None were contacted, because Cowrie only emulates the commands, and
  their presence implies nothing about the owners of those addresses.
- Credentials in the manifests are invented and are not used anywhere.
