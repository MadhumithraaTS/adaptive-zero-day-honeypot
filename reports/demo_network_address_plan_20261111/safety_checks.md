# Safety checks: spoofing, allowlist escape, isolation (design)

| # | Risk | Mechanism | Control (design) | Pre-run check |
|---|---|---|---|---|
| R1 | Test client impersonates the control client, or vice versa | Change its own IP, or send packets with the other's source address | Clients run with `cap_drop: [ALL]`, so they have no `NET_ADMIN` (cannot change addresses or routes) and no `NET_RAW` (cannot craft raw or spoofed packets or ARP replies). Also `no-new-privileges`, a non-root user, a read-only root, and no sysctls. A TCP connection with a spoofed source fails without the return path | `docker inspect` caps = `[ALL]` dropped; `CapEff` = 0 inside each client |
| R2 | ARP/L2 spoofing on the shared bridge | Docker bridges do not filter source MAC/IP per port by default | Requires `NET_RAW`, which is dropped. Fixed per-network MACs. The relay's ARP/neighbour table for 10.250.25.3 and .4 is checked against the registry MACs before and after each run | `ip neigh` (or `/proc/net/arp`) in the relay = registry MACs |
| R3 | An unplanned container joins `demo_ingress` | `docker network connect`, or a misconfigured Compose file | Dynamic pool `10.250.25.8/29` is outside the fixed `.2`–`.4`. The membership check requires exactly 3 endpoints with the expected names, IPs, MACs and container IDs; otherwise the run is aborted. Unregistered peers are rejected by the relay | `docker network inspect cowrie_demo_ingress` = exactly the 3 planned endpoints |
| R4 | A client is recreated with a different address | Compose drift; Docker IPAM | Fixed `ipv4_address` and `mac_address` in Compose. Registry keyed by IP **and** expected MAC. Container IDs recorded per run | As R3, plus an image digest check |
| R5 | Allowlist escape (a rule targets the control client, the relay or anything else) | A wrong proposal or approval | The enforcement allowlist is `10.250.25.3/32` only, held separately from policy. The relay refuses any rule outside it. `10.250.25.2` is protected; the control client is never a target | Rule-validation unit tests (Task 25 S6/S7) |
| R6 | Published-path traffic mistaken for demo traffic | Same relay process | Separate listeners (`10.250.25.2:2222` vs `172.21.0.2:2222`). `ingress_listener` is recorded per mapping. Only demo-listener mappings can be attributable. `172.21.0.1` stays protected | The mapping log's `ingress_listener` matches the listener of each accepted socket |
| R7 | Clients reach Cowrie, the VM or the internet directly | Routing | Clients only on `demo_ingress` (`internal`, isolated gateway). The relay is not a router (no forwarding, no `NET_ADMIN`) | From each client: connecting to 172.22.0.1:2222, 192.168.65.x and 1.1.1.1 fails. A one-time isolation test at implementation, which needs its own approval |
| R8 | The relay is exposed on extra interfaces | Today's `0.0.0.0` bind | Explicit per-interface binds in the attributing relay | Relay listening sockets = exactly the two planned binds |
| R9 | Identity from DNS names or application data | Name collisions; payload text | Attribution uses `getpeername()` only, never names, banners, usernames or forwarded-for text | Unit tests (Task 25 S4) |
| R10 | Correlation ambiguity (port reuse, concurrency, clock skew) | Ephemeral port reuse | Exact tuple plus a time window; zero or multiple matches abstain. The demo runs clients sequentially | Correlation unit tests with injected duplicates |
| R11 | Mapping forgery or tampering | Writable log | Relay-only Ed25519 key, hash chain, external checkpoint | `verify_chain` + signature verification before each assessment |

**Abort rule:** if any pre-run check fails, the demo does not start, and the failure is appended to the controller audit log.
