# Trustworthy relay attribution (design)

## 1. Current state (inspected read-only; `evidence/relay_inspect.txt`, `cowrie/docker-compose.yml`)

- **Relay:** `cowrie-ssh-relay` runs `twistd -n portforward --port=tcp:2222 --host=cowrie --dest_port=2222`. It is Twisted's generic TCP forwarder: it opens a **new** connection to Cowrie per client and **logs nothing** about the mapping.
  - Container: user `cowrie`, read-only root, `cap_drop: [ALL]`, `no-new-privileges`.
  - Networks: `cowrie_internal` 172.22.0.2 and `relay_frontend` 172.21.0.2.
  - Published port: `127.0.0.1:2223` only.
- **Cowrie** sees every connection from `172.22.0.2` with the relay's ephemeral `src_port`. The `cowrie.session.connect` event records `src_ip`, `src_port` and a timestamp.
- **The relay does not see real client addresses either** *(H, unverified)*. Clients reach `127.0.0.1:2223` through Docker Desktop's port proxy, so the relay's peer is a Docker gateway or proxy address, not the client. Policy v1's note says the same for the former network. This must be verified in the implementation phase with a single controlled connection before any design step relies on it.
- **Consequence:** with the current deployment, *no* hop can attribute a client. **Dataset V2 sessions are permanently unattributable**: no mapping was recorded when they were generated, and none can be reconstructed.

## 2. Proposed mechanism: an attributing relay with an exact connection mapping

Replace the generic port forwarder with a small **attributing relay**. Same pinned image, same hardening, Python/Twisted, no new capabilities.

**For every accepted connection, the attributing relay:**
1. takes the client identity **only** from its own accepted socket (`getpeername()`), never from bytes the client sends;
2. checks the restriction list (`enforcement_boundary.md`) before opening the upstream connection;
3. opens the upstream TCP connection to Cowrie and reads **its own local upstream port** (`getsockname()` on the upstream socket);
4. appends one mapping record, then updates it on close.

**Mapping record** (append-only JSONL, one per connection, plus a close record):

| Field | Meaning |
|---|---|
| `connection_id` | UUIDv4, generated by the relay |
| `client_ip`, `client_port` | `getpeername()` of the accepted socket |
| `ingress_listener` | Listener address and port (e.g. the demo ingress) |
| `upstream_local_ip`, `upstream_local_port` | `getsockname()` of the relay→Cowrie socket. Equals Cowrie's `src_ip`/`src_port` for that session |
| `accepted_utc`, `upstream_connected_utc`, `closed_utc` | Microsecond UTC timestamps from the relay clock |
| `bytes_in`, `bytes_out` | Totals at close |
| `restriction_check` | `allowed` or `rejected:<rule_id>` |
| `seq`, `prev_hash`, `record_hash` | Hash chain (as in `threat_assessment/audit.py`) |
| `signature`, `key_id` | Ed25519 over the record (key in §4) |

## 3. Cowrie session correlation

A Cowrie session is attributed to a client **only if**:
1. exactly one mapping record has `upstream_local_ip = src_ip` and `upstream_local_port = src_port` of the session's `cowrie.session.connect`;
2. `|connect_ts − upstream_connected_utc| ≤ 2 s` (a clock-skew budget; both run on the same host);
3. the mapping's `closed_utc` is absent or later than the connect timestamp;
4. the mapping record's signature and chain verify;
5. the client IP is not a trusted proxy, protected or shared (unchanged attribution rules).

**Outcomes** (new attribution states; they require a new version of `threat_assessment` and of the attribution config):

| Case | State |
|---|---|
| Exactly one valid match | `attributable_via_proxy_mapping` |
| No match | `unattributed:mapping_missing` |
| More than one match (port reuse inside the window) | `unattributed:mapping_ambiguous` |
| Signature or chain invalid | `unattributed:mapping_untrusted` |
| Mapping log unavailable | `unattributed:mapping_unavailable` |

All non-`attributable` outcomes block proposals (gate 5). Matching is exact on the TCP 4-tuple and time; there are no fuzzy or "closest" matches.

## 4. Integrity protection

- **Signing key.** A relay-only Ed25519 key (`relay-mapping-key`) is mounted read-only as a Docker secret. Only the **public** key is given to the assessment side, so the assessment can verify mappings but never forge them.
- **Mapping log storage.** The log goes to a dedicated volume that the relay can only append to. Its chain head is checkpointed externally (`audit_and_recovery.md`).
- **Cowrie's own logs are unchanged**, and correlation uses only fields Cowrie already emits.

## 5. Expiry and retention

- A mapping is usable for correlation only for sessions whose connect time lies in `[accepted_utc, closed_utc]` plus the skew budget.
- Mappings are retained as long as the Cowrie logs and audit logs they support (`audit_and_recovery.md` §3).
- Expired or rotated logs remain verifiable through their checkpoints.

## 6. Spoofing protection

- **No forwarded headers, ever.** SSH has no forwarding header, and the relay never parses client payload for identity. The relay does not accept the PROXY protocol from clients. Any future trusted hop would require mutual authentication and its own signed mapping.
- **`threat_assessment` keeps ignoring forwarded-for style fields** (already implemented and tested).
- **The `127.0.0.1:2223` published path stays unattributable** while its peer is a Docker proxy address: that peer is listed as a trusted proxy or protected address, never an attacker identity.

## 7. What changes (future, each requires approval)

- A new relay implementation and image entrypoint for the relay service only. Cowrie and `cowrie_internal` are untouched.
- A new demo ingress network (`enforcement_boundary.md`).
- Attribution config v2: a non-null `proxy_client_mapping` with public key, log path and skew budget.
- `threat_assessment` 1.1: the new attribution states and correlation.

The current attribution config (v1, `proxy_client_mapping: null`) stays unchanged and valid for existing data.
