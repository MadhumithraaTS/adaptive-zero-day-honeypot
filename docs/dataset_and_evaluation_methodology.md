# Dataset and Evaluation Methodology

This note documents the datasets used in the project, which data trained the clustering model, and
how training, reference, and evaluation data are kept separate. It is written so that the provenance
and the train/evaluation split can be stated precisely in the report.

## 1. Datasets and their roles

The project uses three distinct bodies of session data. They are **not** interchangeable, and each
has a single, well-defined role.

| Dataset | Sessions | Origin | Role |
|---|---|---|---|
| `model_selection/behavior_features.csv` | 1,800 | Synthetic, generated by `scripts/generate_dataset.py` | **DEC training set** |
| `data/` pipeline runs (e.g. baseline backup) | ≤ 54 | Real Cowrie honeypot | Pipeline *test* runs that **apply** the trained DEC; not training data |
| `dataset_builder/runs/train_v1`, `.../eval_v1` | 3,125 / 1,232 | Real Cowrie honeypot, labelled at generation time | Independent **reference** and **evaluation** sets (and the public release) |

### 1.1 DEC training set (synthetic)

The Deep Embedded Clustering (DEC) model was trained on `model_selection/behavior_features.csv`,
produced by `scripts/generate_dataset.py`. Key properties:

- **1,800 sessions** across 8 categories: `reconnaissance`, `botnet_malware_download`,
  `privilege_escalation`, `brute_force_only`, `evasion_anti_forensics`, and three zero-day types
  (`zero_day_obfuscated_memory_attack`, `zero_day_buffer_overflow`, `zero_day_covert_tunnel`).
- **13 distinct source IP addresses**; label split 1,536 attack / 264 normal.
- **Fully synthetic:** `generate_dataset.py` fabricates Cowrie JSON events directly in Python. This
  data was never produced by the honeypot.

### 1.2 Real honeypot data

The sessions under `data/` were captured from the Cowrie honeypot during pipeline development. They
are **not** training data: the pipeline loads the pre-trained DEC artifacts and applies them. In the
earlier runs every session is labelled `normal` because the original attack generator did not record
which profile produced each session; those runs are therefore useful for pipeline testing but not as
a labelled evaluation set.

### 1.3 New labelled dataset (`dataset_builder/`)

The tooling in `dataset_builder/` generates real honeypot sessions **with ground-truth labels** by
recording, for every generated session, the profile that produced it (see
`dataset_builder/README.md`). This yields a labelled, reproducible dataset suitable for both
evaluation and public release.

## 2. The DEC model

The clustering model is fixed and loaded from saved artifacts
(`ml/cowrie_dec_integration_skeleton/ml/cowrie_dec/artifacts/`). From its `config.json`:

- **Unsupervised:** DEC clusters on **17 numeric features** and never reads `attack_cat` or `label`.
  Labels are used only (a) to compute external clustering metrics and (b) to build the novelty
  reference. The 17 features are a subset of the 24 UNSW-NB15-style features
  (`dur, spkts, dpkts, sbytes, dbytes, rate, sload, dload, sinpkt, dinpkt, sjit, djit, tcprtt,
  synack, ackdat, ct_srv_src, ct_src_ltm`).
- **Architecture / preprocessing:** latent dim 4, **3 clusters**; inference reproduces the training
  pipeline exactly — median imputation → `log1p` on skewed features → saved `StandardScaler` → DEC.
  No encoder or scaler is re-fitted at inference time.

## 3. Train / reference / evaluation separation

Because DEC is pre-trained and frozen, "training" does not re-occur when the new dataset is used.
Separation is maintained at two layers.

### 3.1 Independence from the DEC training set

The new honeypot dataset shares **no sessions** with `model_selection/behavior_features.csv`, and is
produced by a different mechanism (real honeypot vs. synthetic generator). Evaluating the DEC on it
therefore involves no in-sample reuse of the model's training data.

### 3.2 Reference vs. evaluation split for novelty assessment

Novelty assessment (`scripts/novelty_assessment.py`) builds a catalogue of **known behavioural
signatures** from a reference set and classifies new sessions as *known-like* or *potentially novel*.
The script includes an explicit `reference_independence` check that flags any assessed session whose
ID also appears in the reference catalogue, warning that such results are in-sample. To satisfy it,
two separate runs are generated:

| Run | Seed | Generated sessions | Dataset rows | Held-out category | Use |
|---|---|---|---|---|---|
| `train_v1` | 1 | 1,500 | 3,125 | **excluded** | Build the reference ("known") signatures. |
| `eval_v1` | 2 | 600 | 1,232 (106 `exfiltration`) | **included** | Evaluate; contains a category the reference never saw. |

Dataset rows exceed generated sessions because every failed-login attempt is a separate SSH
connection and therefore a separate Cowrie session. The two runs share no session IDs.

The held-out category (`exfiltration`) is the basis of the zero-day / novelty test: it is absent
from both the reference signatures and the DEC training set, so a correct system should flag it as
potentially novel.

## 4. Evaluation metrics

- **Clustering quality:** with verified ground-truth labels, `run_dec_evaluation.py --labels-verified`
  reports Adjusted Rand Index (ARI) and Normalized Mutual Information (NMI) between DEC clusters and
  the true categories. (Without `--labels-verified` these are omitted, because unlabelled sessions
  are filled with `label=0`.)
- **Novelty detection:** on `eval_v1`, the fraction of held-out novel sessions correctly flagged as
  *potentially novel*, versus the false-positive rate on known categories.

## 5. Limitations to state honestly

1. **The DEC was trained on synthetic data.** Its clusters reflect `generate_dataset.py` behaviour,
   not wild capture.
2. **Domain shift between training and evaluation.** Training data is synthetic, multi-IP, and uses
   8 category names; the new evaluation data is real-honeypot, single-source-IP
   (all traffic originates from the local generator), and uses different category names. This tests
   generalization rather than memorization, but it is a genuine distribution shift and should be
   named as such.
3. **Source-IP features carry little signal in the new data.** Because all new sessions originate
   from one address, IP-derived features (e.g. the `ct_*` connection counts) are near-constant and
   should not be over-interpreted.
4. **"Never saw a zero-day" would be inaccurate for the DEC.** The DEC training set already contains
   three `zero_day_*` categories. Since DEC is unsupervised, those sessions merely shaped the
   clusters; the model did not learn to label them. The clean novelty claim rests on the held-out
   `exfiltration` category in `eval_v1`, which is absent from both the DEC training set and the
   reference signatures — not on the DEC training composition.
5. **One held-out category.** The novelty test uses a single unseen behaviour (`exfiltration`,
   106 sessions). Results show whether that behaviour is flagged; they do not on their own establish
   detection across many kinds of novel attack.
